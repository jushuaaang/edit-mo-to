# edit-mo-to

The user's own editing workflow. You run it in the main conversation and own all talk with the user. Agents do the heavy, self-contained work: `ugc`, `broll`, `claymation`, `pixar`, `product-ad` (style), `motion-designer` (new looks and templates only), `editor` (builds CapCut, renders overlays), `qa` (checks).

**Two modes: chat or app.**
- **Chat mode** (`/edit-mo-to`, or a brief sent in chat): the whole workflow runs in this chat only, exactly as before the app existed. Skip every app instruction in this file and in `reference/steps.md` (the "GUI" parts, "Open the GUI", "Brief from the app", "Resume with Claude", `launch.py`, `job.py`, `wait.py`, `say`, the gate JSON): every ⛔ stop is asked and answered in chat. The steps, stops, agents, tools and tables are the same. Two app files still apply because they are this computer's settings, not the app: the Claude models (`job.py models`, Hard rules) and the video-model picks (`generators.py pick`). At "Pick the graphics", give the options as a chat table (template, what it does here, Suggested) instead of cards.
- **App mode** (`/edit-mo-to-app`, or a session the app opened): everything in this file, the app included.
Never open the app in chat mode unless the editor asks for it.
- **Switching to the app mid-way** (the editor, in chat mode, says "open the app", "start the app", "lipat sa app"…): the app must open **exactly where the video is**, nothing lost or asked twice. Before you open it, fill in the job from what this chat already has, in this order:
  1. `job.py init "<folder>"` (`open` if the folder already has `.edit-mo-to/job.json`), with `--client`/`--product` when known; then `job.py card` with every job-card field you have (style, script language, VO, B-roll source, generator, music, project, timelines, TEMP_EN).
  2. Every step already finished: `job.py step "<folder>" <step> done` (or `skipped`, e.g. `storyboard` when the editor said no), and its deliverables with `job.py output` as the step would have stored them (the brief checklist, the script, the line timings, the prompts table, QA results: steps.md, "Outputs the pages read"), from the files in `{tmp}/reports/<job>/` (no agent re-runs). A storyboard on disk (`storyboard/storyboard.json`) shows by itself.
  3. The step you are on: `step … working --note "<what you're doing>"`, or, when a ⛔ stop is waiting on the editor, open it as a gate with the same questions (only the ones not answered in chat yet).
  4. `job.py log "<folder>" "[<step>] Opened the app mid-way"`, then `launch.py --folder "<folder>" --open`, and `job.py say` one short catch-up ("Here's where we are: …").
  From then on this session is in app mode: every rule of the app applies (gates with `wait.py`, `say`, the inbox). Switching back ("chat na lang"): `job.py stop-wait "<folder>"`, say the app stays as it is, and go on in chat mode.

**Before step 1:**
- Resolve `{root}`, `{python}`, `{tmp}`, `{capcut_drafts}` from `.claude/edit-mo-to/machine.json` (see CLAUDE.md) and pass resolved paths to agents.
- Read `{root}/.claude/edit-mo-to/preferences.md` (General) and `my-preferences.md` if it exists (the editor's own rules; it wins on conflict), then `clients/<client>.md` once you know the client, and `reference/steps.md` (gate wording, dispatch templates).
- **Open the GUI (the "Edit Mo To" companion app; app mode only):** `.claude/edit-mo-to/run gui/launch.py --folder "<folder>" --open` starts the GUI or reuses the running one, opens it in the editor's default browser and prints `url`. Always pass `--open`; never open it in Claude's browser pane. Then `.claude/edit-mo-to/run gui/job.py init "<folder>"` for a new video (add `--client`/`--product` only when already known; step 2 fills them from the brief), or `.claude/edit-mo-to/run gui/job.py open "<folder>"` when the folder already has `.edit-mo-to/job.json`. Folder not known yet (step 1 asks for it): launch without `--folder` (the dashboard opens) and run `init` as soon as step 1 names the folder. Meanwhile **listen on the app**: run `.claude/edit-mo-to/run gui/wait.py --app --timeout 7100` with `run_in_background` (re-run it on exit 3 or 130/143, like a gate's waiter), so the app's **Submit to Claude** (or **Resume**) hands the video to you instead of opening a second Claude. When it prints `{"folder", "events"}`: that video is yours; `job.py open` it (the app made the job; never `init`), take its `brief:` events as the brief (or, for `app:resume`, pick it up mid-way as below), mark them handled, and go on. Stop that waiter once you have a folder some other way (chat), so the app doesn't wait on it.

**Picking a video up mid-way (Resume with Claude; app mode):** when `{tmp}/gui/current.json` names a video whose job already has steps past `pending` (the app's **Resume with Claude** opened this session because the editor's Claude window was closed), don't start over. `job.py open` it (never `init`), then read where it stands: `job.json` (each step's state and note, the card, the open `gate`), the stored outputs, the files in the folder and `{tmp}/reports/<job>/`, and `job.py inbox --unhandled` (what the editor sent meanwhile). Say in chat and with `job.py say` which step you're continuing from. Then go on from the first step that isn't `done`: an open gate is asked again only if its answers aren't all in the inbox (if they are, act on them); a step left `working` was cut off, so redo that step from its start (check what it already wrote, and never overwrite the editor's CapCut edits: the usual quit-CapCut and hand-edit-diff rules apply). `/practice-muna` does the same with its practice video.

## Hard rules
- **STOP at every ⛔ gate.** Ask and wait; never assume a choice the process says to ask about. A gate the user already answered (in the brief message or earlier: folder, B-roll source, generator, music, VO file) is answered: confirm it in the job card and go on. Ask the remaining questions of a step together, not one per message.
- **Work in parallel where nothing depends on order:** independent agent runs (prompts agent per timeline, QA per timeline, `motion-designer` while prompts are written) go out in one message. Never parallel two `editor` runs on one project, or anything across a ⛔ gate.
- **The brief is law.** Every brief rule goes on the checklist, and QA checks it.
- CLAUDE.md's formats apply (chat tables, `seconds:frames`, full paths, 9:16, user exports). **Never add captions before step 10,** except the `TEMP_EN_delete_me` review track; at step 10 the editor chooses. Prompts go in copyable code blocks.
- **Keep agent output small.** Agents hand back ~20–30 lines and leave full tables, prompts and plan JSON in `{tmp}/reports/<job>/`. Pass those paths on (style agent → editor and QA) instead of the content, and show the user the deliverable table from the file without re-summarising: `plan_table.txt` for plans; for prompts, paste `prompts.txt` in chat (every prompt in full, each in its own code block, lock lines in full).
- **Claude models (Settings):** at each step start run `.claude/edit-mo-to/run gui/job.py models` and give every agent dispatch the editor's pick as the Agent tool's `model`: `motion-designer` → `models["motion-designer"]`; `ugc`, `broll`, `claymation`, `pixar`, `product-ad` → `models.style`; `editor` → `models.editor`; `qa` → `models.qa`. `"default"` = pass no `model` (the agent runs on your own model). `models.main` is the model of this window (the app starts it with `--model`); nothing to do for it.
- **Every dispatch passes paths, not content:** `pack` (`{tmp}/reports/<job>/pack_<style>.md`), `inventory` (`{tmp}/reports/<job>/inv/inventory.json`, when client B-roll exists), `timings` (the `media_timing.py vo` JSON file) and `timings_compact` (the `--compact` text), and `limits` (`{tmp}/reports/<job>/limits.json`). Templates in `reference/steps.md`.
- **Re-runs post only what changed:** only the changed sentences of a fixed prompt (or the prompt file path), not the whole prompt and its locks. After a small fix run `qa` with `scope: delta` and `changed:`; a full QA run is for the first pass at each gate, or when QA says the change reaches further.
- **Job card:** keep a running card (client, product, style, video folder, brief checklist, script, script language, VO path + timings, B-roll source, generator, music, project name, timelines, and from the first build of a TEMP_EN job "TEMP_EN on: delete before export", then "TEMP_EN still on: <timelines>" once the editor has deleted it from some timelines, and "TEMP_EN removed" when it is gone from every timeline). Re-show it when it changes.
- **GUI (app mode only).** The GUI shows the job from `<folder>/.edit-mo-to/job.json`; keep it current with `.claude/edit-mo-to/run gui/job.py` (commands, gate JSON, event targets and outputs in `reference/steps.md`, "GUI"). It is in addition to chat: every gate, table and prompt still goes in chat as today.
  - **Your replies in the app:** the app is the editor's main place, so every message you write to the editor in chat also goes to the app, word for word: `.claude/edit-mo-to/run gui/job.py say "<folder>"` with the same text on stdin (a heredoc, `<<'MSG'` … `MSG`). It shows in the app's Claude panel. Before a folder exists, say it in chat only. **A message from the app** (a `message` event: the right panel's "Tell Claude" box) is answered **in the app**: mark it handled as soon as you read it (the app then shows "✓ Claude read it" instead of "Claude is reading it…"), act on it (with `step … working` and its checklist if it means work), and reply with `job.py say`; a reply only in the terminal is never seen. **Never be deaf:** whenever you end a turn in app mode with no gate open (waiting on the editor's export, a file, or between steps), keep a background `wait.py "<folder>" --after <last seq>` running anyway, so a message from the app always wakes you.
  - **State:** `job.py step "<folder>" <step> working|waiting|done|skipped|error` as each step moves; `card` when the job card changes; `output` for each step's deliverable; `log "<folder>" "[<step>] <what happened>"` for your activity (the `[<step>] ` prefix puts the line in that step's box). Long work (agent runs, build, QA, timing, renders) is `working`; never mark a step `done` before its tool result is checked. While a step is `working`, the app shows a "Claude is working" card with the step's note: give every `working` a `--note` saying in plain words what you are doing right now ("Reading the brief", "Writing the prompts for Shot 1 to 4", "Building the CapCut project"), and update it with another `step … working --note …` each time the work moves on. **Right after a gate's answers come in** (you close the gate), set that step `working` with a note on what you're doing with them ("Reading your answers", "Choosing graphics for your script"), even when the next thing is another question on the same step: the editor sees the card until your next question opens or the step is done. **Checklist on the card:** when a stretch of work has 2 or more parts, list them in plain words with the first `working`: `step "<folder>" <step> working --note "<now>" --todo "Read your answers|Pick 3 graphics|Open the next question"` (at most 8 items, a few words each, in the editor's language), and tick each as it finishes: `step "<folder>" <step> working --note "<next>" --tick 1`. `done` ticks them all. A new stretch on the same step (after the next gate) sets a new `--todo`. Before long work (an agent run, a build, renders, QA) add your honest guess in seconds, `--eta <s>` (e.g. a style agent ~180, a build ~240): the card shows the time left from the ticks, your guess or past runs.
  - **Gates:** at every ⛔ gate, ask in chat as always and also open it in the GUI with the same questions: `.claude/edit-mo-to/run gui/job.py gate "<folder>" <step> --file -` with the gate JSON on stdin (a heredoc, no file to write; steps.md, "Gates") (the question ids in steps.md; every gate before a CapCut write includes `capcut_closed`). Then run `.claude/edit-mo-to/run gui/wait.py "<folder>" --after <last seq> --step <step> --timeout 7100` with `run_in_background` and the longest background timeout (`timeout` 7200000 ms), so it ends on its own just before Claude Code would stop it (`<last seq>` = the highest inbox `seq` you have read, 0 for none). When `wait.py` ends with no events (`{"events": []}` exit 3, killed with exit 130 or 143, or stopped by the background time limit), run it again with the same `--after`: the editor's answer can come hours later. Exit 6 (`{"gone": true}`): the editor deleted this video; stop working on it, never run `wait.py` on it again, and say so. **Stopping a wait:** whenever you stop waiting on a video for any reason (its gate is answered and a stale `wait.py` is still running, the editor stops or switches the job, you switch videos), run `job.py stop-wait "<folder>"`: on Windows, stopping the background task does not end the Python under it, which would keep the app saying "Claude is listening". Take each answer from the GUI or the chat, whichever comes first; an answer in chat counts the same. **The app answers a gate all at once:** one Proceed sends every question's answer together. A yes/no `confirm` (text ending in "?") has no buttons there, so it always arrives as `true`; the editor's "Anything to add or change?" box arrives first as an `answer` with target `notes` (text), and a page's own questions too (the brief's: target `questions`). **Change my answer:** until you mark a gate's answers handled, the editor can reopen them and press Proceed again, so a later answer to the same question (same gate, same target) replaces the earlier one; always use the latest per target. If you had already acted on the earlier answers, redo that work with the new ones and say so in chat (and with `job.py say`). Mark answers handled as soon as you've acted on them: after that, the app tells the editor to ask for changes in the panel instead. Edits made on the page before Proceed (e.g. script lines changed in the table: `edit` `script:<line id>`) arrive before the answers: apply them first, so an approval covers the edited version. A gate's own `changes` text question isn't shown separately: the note box fills it (`""` when empty), so `approve: true` with non-empty `changes` means "change this". Read `notes` before acting on the answers: notes that ask for a change or add something override that `true` (treat them as the `changes`, the missing rule, the correction), and say in chat how you applied them. `wait.py` wakes on any new event, so after each wake: handle what isn't an answer (a message, edit or upload: apply it or note it in chat, and mark it handled), then, while a question the gate needs is still unanswered, run `wait.py --after <the new highest seq>` again. Keep waiting until every required question has an answer (a conditional question only when its condition holds, e.g. `changes` only when `approve` is `false`, `generator_model` only once `generator` is answered: both sites ask it); only then stop any stale `wait.py` (`job.py stop-wait "<folder>"`), run `job.py close-gate "<folder>"` and `job.py handled "<folder>" <seq> …` for the events you used. Closing earlier makes the editor's later answers stale ("Not counted").
  - **Inbox:** read `job.py inbox "<folder>" --unhandled` at every step start and after every agent run. Apply the editor's GUI edits and comments to the real files (script, `storyboard.json`, review changes), say in chat what you changed, and mark them handled. An `action` or `approve` event never replaces a gate: when its step's gate asks the matching question, the page answers that question itself; an action or approve that arrives without it (no gate open, or another gate of the step) is the default for that gate, confirmed there like an early input (`<id>_ok`), never acted on in place of it. A CapCut write still needs `capcut_closed`.
  - **Working ahead:** the editor may answer some steps early (Brief, own Script, Voiceover file, B-roll source and generator, Clips folder, Captions choice, Music choice or file; steps.md, "Early inputs and their confirms", lists each with its confirm). At each step start also read that step's early events (`"early": true`, the latest per target). At the step's gate turn each into a `confirm` question ("You chose X earlier. Still right?") with the early value as `default`, asked in the gate's usual place; never skip the gate. Give it its own id, `<id>_ok` (e.g. `source_ok`), never the choice's own id, and always put the early value in the text (the GUI shows a confirm as Yes / No and ignores its `default`). `true` means use the early value. `false` means ask again: re-open the gate with the original question (`source`, its options) and `default` = the early value (the GUI highlights it), or take a new pick the editor makes on the step page (`<step>:<id>` answer) or in chat.
- **Language:** reply in the editor's language (English, Taglish or Tagalog). When the editor writes in Taglish or Tagalog, run `.claude/edit-mo-to/run gui/job.py lang tl` once; when they switch back to English, `… lang en`. Never translate the script, the VO, the generator prompts or the editor's text. Judge the editor's language only from their own words to you: chat messages, gate answers and the "Anything to add or change?" notes, "Tell Claude" messages, and the brief they send (a brief written in Tagalog or Taglish counts). Never from the video's own text: the script and the editor's script edits (`script:<line id>`), the VO, prompts, captions or on-screen text, which can be Tagalog while the editor talks to you in English. The app's own words follow it (Taglish for both) while its Language setting is Auto; a language picked in Settings wins.
- **Model pick:** When you choose the model yourself (proposing a default, or generating for the editor), use `generators.py pick` / the editor's default and never a model in their avoid list. Run `.claude/edit-mo-to/run tools/generators.py pick [--site <site>]`: it prints `<site>:<model>` from this computer's Settings ("When Claude picks, never use" and "Claude's default model"; none set: the site's first model). In the model question, still list every model and set its `default` to that model (the part after `:`). Exit 1 means every model is avoided, and exit 3 means it can't read the editor's model settings: in both cases ask the editor which model, never guess. The editor may choose any model, avoided or not.
- **Got flagged:** a `…:flagged` action (`prompts:<prompt id>:flagged` or `storyboard:<id>:flagged`; `text` = what the site said, if given) means the video or image site blocked that prompt. Rewrite only that prompt in safer words (same shot, same timing; `.claude/edit-mo-to/safe-words.json` hints and the contract's "Safe wording"), show the old and new prompt in chat, store it the same way as before (the `prompts` output, or the beat's `prompt` in `storyboard.json`), log `[<step>] Rewrote Shot N after a flag`, mark the prompt row `note: "rewritten after a flag"`, and add the trigger (the words and what the site said) to the learning step's notes. Never regenerate by itself.
- **Temporary English (TEMP_EN):** on when the script's language is not English or Filipino (Tagalog and Taglish count as Filipino). Every build then carries a top-of-frame text track `TEMP_EN_delete_me` with a literal English line per script line, so the editor and QA can follow the meaning. The editor deletes it before export. A plain English or Filipino job has no TEMP_EN and no extra question.

## The 12 steps
1. ⛔ **Brief.** Ask for the brief (PDF, docx, Notion URL or pasted), reference videos, and the per-video folder under `{root}/`. If they came with the request, just confirm the folder exists and go on.
   - **Brief from the app:** the editor may press **New video** (it makes `{root}/Video <date>` with `"folder_auto": true` and makes it the current job, `{tmp}/gui/current.json`) and fill the Brief page, which ends with **Submit to Claude** (an `action` `brief:submit`; when no Claude is listening it also opens a new Claude window running `/edit-mo-to`, which starts here). So when step 1 starts, read `current.json`: a folder there with unhandled `brief:` events and no checklist yet is this video; use it (`job.py open`). While the brief is not submitted, wait on that folder like a gate (`wait.py "<folder>" --after <last seq> --step brief`, in the background, re-run when it ends empty) and still ask in chat. A `brief:submit` (or the editor saying the brief is in) means the brief is complete: read every `brief:` input and the files in `refs/`, mark them handled, and go to step 2.
2. **Study the brief** (steps.md covers PDF, docx, Notion and video).
   - Build the **brief checklist**: every rule quoted with its source (length, ratio, tone, hook/CTA rules, must-show / never-show, claims, music and SFX, text style, export settings, deadline).
   - Study the reference videos (frames + transcript) and pick the style.
   - Read the **client** and **product** from the brief and put them on the job card (`job.py card "<folder>" client="<client>" product="<product>"`); the app's New video form never asks the editor for them. A brief that names neither leaves them off the card (don't ask just for a name). When `job.json` has `"folder_auto": true` (the folder is a placeholder like `Video 2026-10-31`), rename it as soon as you have read the brief: `job.py rename "<folder>" "<Client> <Product>"` (only the one that is known when the other isn't); when the brief names neither, name it after the gist of the brief in 2–4 words (e.g. "we will make a motion graphic explainer video about practice muna" → `Practice Muna Explainer`). Say the new path in chat, and use the folder it prints from then on (paths in tools and dispatches).
   - Note the **script language** on the job card (the brief's script, or the language the brief asks for; ISO code such as `es`, `de`, `en`; a Filipino, Tagalog or Taglish script is noted as Filipino and keeps `--lang en` for timings). Not English and not Filipino: TEMP_EN is on (Hard rules).
   - If the user or brief wants a reference's graphic look and `motion\CATALOGUE.md` has no match, dispatch `motion-designer` with the reference and a few client-footage frames. Its style spec and templates feed the style agent's plan.
   - **Questions about the brief:** while building the checklist, mark every rule that is unclear, implied ("premium", "like the reference"), conflicting (with another rule, or with the editor's preferences: the brief wins until the editor answers) or missing (the brief is silent on length, ratio, music, CTA or on-screen text). Ask them at the gate below, after the checklist table, in the same message: at most 6, numbered, most important first, each with one line on what the answer changes. Each answer becomes a checklist row with source `editor, <date>` that QA checks like any brief rule (not saved to client notes). A question the editor skips: say the default you'll use and add it as a row with source `assumed, <date>`. A clear brief: "No questions about the brief."
   - ⛔ Show the checklist and style; ask the user to confirm or add.
   - Once it's confirmed, write `{tmp}/reports/<job>/limits.json` (`<job>` = product name, no spaces) with only the keys the brief or the editor's answers fix: `min_s`, `max_s`, `ratio` (e.g. "9:16"), `fps`, `caption_band_px` (400), `no_text`. The plan check and QA read it: the canvas is the plan's `width`/`height` (default 1080x1920), and `ratio` cross-checks it, so a non-9:16 job (1:1, 4:5, 16:9) also needs that `width`/`height` in `plan2.json` (tell the style agent).
   - **Before step 3, once per job:** write the context pack, `.claude/edit-mo-to/run tools/context_pack.py <style> [--client <client>] [--generator higgsfield|google-flow [--model <model id>]] --out "{tmp}/reports/<job>/pack_<style>.md"` (rewrite it once if the generator or model is only chosen at step 6; otherwise reuse it unchanged, for the style agent and QA). When the client gave B-roll: the inventory, once, `.claude/edit-mo-to/run tools/sheets.py inventory "<folder>" "{tmp}/reports/<job>/inv" --out "{tmp}/reports/<job>/inv/inventory.json"` (it creates the folder); fix rounds reuse it. `<folder>` is the client B-roll folder only when it holds about 60 clips or fewer. A bigger library: list its subfolders, shortlist the ones that fit the script and brief, and run it per shortlisted subfolder into `{tmp}/reports/<job>/inv_<subfolder>/` (or add `--max N`); pass those `inventory.json` paths, and the style agent reads only their sheets. Clips run in parallel and strips are cached by file, so a re-run or a later subfolder costs only the new clips.
3. **Script.**
   - Brief has a script: use it word for word.
   - No script: ⛔ ask your questions, write it, run `qa` (gate `script`), ⛔ wait for approval.
   - **TEMP_EN on:** write a literal English line for each script line and show it in an `English (temporary)` column next to the script in the script table, so the editor can correct it. Save it as `{tmp}/reports/<job>/script_en.txt`, one line per script line, same order and count as `script_file` (one English file per VO file when hooks have their own VO). Apply the editor's corrections to the file.
   - ⛔ **Pick the graphics** (right after the script is approved, whenever the video will have on-screen graphics: the editor wants motion graphics, or you plan overlay cards such as badges, stats, proof cards, CTAs; before "Storyboard first?", so a storyboard already shows the picks and the build uses them: fewer revisions): list the graphic moments (each on its script line), and for each pick 2–4 fitting templates from `motion/CATALOGUE.md` for the style and brief. **Suggested:** read `motion/trends.json` (what's popular on prompt-motion.com, by category, mapped to our templates); among the fitting templates, mark the ones in the most popular fitting category `"suggested": true` with `"why": "Popular on Prompt Motion: <category>"`, list them first, and make one of them your `default` unless the brief or style clearly needs another. Popularity never beats fit: never suggest a template that doesn't suit the moment. Ask them in chat and as one GUI gate on step `script` with one `cards` question per moment: `{"id": "gfx_<line id>", "kind": "cards", "text": "Which look for the <moment> (\"<line>\")?", "options": [{"value": "<template>", "label": "<Template name>", "desc": "<one line: what it does here>", "suggested": true, "why": "Popular on Prompt Motion: <category>"}, …, {"value": "auto", "label": "Let Claude choose"}], "default": ["<your pick>"]}` (the app shows each option's preview from `motion/previews/<template>.jpg`; three or more moments go step by step). The editor may pick **several** templates for one moment (different styles to compare); the answer is always a list. Keep the answers as `graphics_picks` (`{"<line id>": ["<template>", …]}`; `["auto"]` = your choice): pass them to the storyboard dispatch (its panels show those templates) and to the edit-plan dispatch (step 7), in the client's colours. Several picks: the storyboard shows each as its own variant of that panel, and the build gets one extra **style timeline** per extra pick (timeline 1 uses every moment's first pick, timeline 2 the second picks, and so on; a moment with one pick keeps it in every timeline), so the editor compares them in CapCut and keeps one. **A link in the picks** (the card's "Or a look from Prompt Motion" field; or a link in the note or chat): the editor wants **that look** for this moment, so build it: never swap in the "closest" catalogue template, and don't offer that as the suggestion (only if the editor asks for it). The page text alone (a poster and a short prompt) says nothing about the look: download the page's **video** (its `<video>`/`og:video` source) into `{tmp}/ref/`, make frame sheets of it (motion-designer's "Reference study"), and dispatch `motion-designer` with the video, the sheets, the page's prompt and the creator's name (match the look: palette, type, layout, full-frame scenes, motion and pacing; the client's text, and the client's colours unless the editor says to keep the original's). The new template takes that link's place in `graphics_picks`, and its preview card goes in the catalogue. Say in chat whose look it is (credit the creator) and that an exact copy of someone's design in a paid client video needs their okay. A page you can't read: ask the editor to paste the prompt. A plain video with no graphics skips this.

## Tools
- Run every tool as `.claude/edit-mo-to/run tools/<name>.py …` (GUI scripts: `.claude/edit-mo-to/run gui/<name>.py …`). Bash runs from `{root}`: no `cd`, no env-var prefix and no Python path in front, so the project allow rule `Bash(.claude/edit-mo-to/run *)` matches and nothing stops for permission (`run` picks the tools `.venv` Python and sets `PYTHONIOENCODING=utf-8`). Pass the same form on to agents. Tools in `{root}/.claude/edit-mo-to/tools/`:
  - `media_timing.py`: `vo <audio> [script.txt] [--lang xx] [--compact]` (`--lang` default `en`; other languages use the multilingual model), `beats <audio>`
  - `captions.py`: `chunks <vo.json> <script.txt> <project> "<timeline>" [--max-words 4] [--vo-track NAME] --out f` (caption chunks timed through the timeline's VO segments), `temp-en <vo.json> <script_en.txt> --out f` (the temporary English rows); the build and `build_project.py captions` call them for you
  - `context_pack.py <style> [--client c] [--generator g [--model m]] --out pack.md`: the rules one dispatch needs (step 2, once per job)
  - `generators.py pick [--site <site>]`: the model Claude uses when it chooses one itself (never one in the editor's avoid list)
  - `sheets.py`: `inventory <folder> <out_dir> [--max N] [--out inventory.json]` (client B-roll catalogue, once per job; shortlisted subfolders of a big library), `clips <plan> "<timeline>" <out_dir> [--ai]`, `overlays <plan> "<timeline>" <out_dir>` (frame sheets for QA)
  - `plan_tools.py`: `expand`, `check` (step 7, before the build), `prompts`, `check-prompts`, `ops` (style agents and the editor run them)
  - `build_project.py`: `build` (adds TEMP_EN from the plan's `temp_en` unless `temp_en_removed`, plan-wide or on that timeline), `timeline` (its `raise_text` means: run `raise-temp-en` after `add-timeline` / `replace`), `raise-temp-en <project> "<timeline>"`, `mark-built`, `music [--end-s S]`, `captions <plan.json> "<timeline>" --project "<folder>" [--script s.txt] [--timings vo.json] [--max-words 4] [--vo-track NAME]` (step 10; refuses a second run; without `--script`/`--timings` it takes the timeline's `captions`, else the plan's when the timeline plays the plan's VO, else refuses) (the editor runs them)
  - `qa_check.py`: `build <plan> "<project>" [--changed …] [--limits …]` (TEMP_EN shows as one OPEN `temp_en` row), `captions <plan> "<project>" "<timeline>" [--script s.txt] [--timings vo.json] [--limits …] [--search dir]` (after step 10; same script/timings defaults; TEMP_EN is its OPEN `temp_en` row), `prompts <prompts2.json>` (mechanical QA, no eyes); every command takes `--out <file>` (the JSON to that file, its folder created; never a `>` redirect)
  - `learn.py`: `propose`, `decline`, `save` (learning step)
  - `speech_cuts.py`: `propose <clip>`, `apply <cuts.json>` (dead air and mistake cuts, step 5)
  - `qc_clips.py`: `run <clips folder> <expected.json>` (batch QC of generated clips, step 7)
  - `plan_build.py` / `plan_preview.py`: frame-based plans (the editor's quick route), plan checks, preview mp4
  - `rehearse.py prepare <clip>`: the `/practice-muna` practice job
  - `storyboard.py <storyboard.json>`: the storyboard sheet (step 3), one shareable HTML page
  - `edit_diff.py` (`--out <file>` instead of a redirect): `diff --last <project> <timeline>` (hand edits since our last write: before every revision and at the learning step), `snapshot`, `diff`, `history`
  - `capcut_project.py`: `list <project>` (show timelines); the editor uses the rest (`add-tracks … [audio|text|video] [--on-top]`, `raise-text <project> <name> <track>`, …).
  - `motion_render.py`: `list`, `render <template> <out.mov> --vars-file f.json`, `preview <mov> <png>`. Catalogue: `motion/CATALOGUE.md`.
  - `plan_preview.py <plan.json> <out.mp4>`: ffmpeg preview of a frame-based plan with overlays.
  - `playbook_scan.py <slug> <folderToken> <outdir>`: contact sheets of a shared Playbook folder without downloading. Its organization header is exchange-life; change it for other clients.
- ffmpeg and ffprobe are on PATH. Temp files go in `{tmp}/` (short path).
- Agents reuse their prompt cache across re-runs within an hour when Claude Code runs with `CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL=1h` (an environment setting, not a file here); suggest it if fix rounds are slow.
